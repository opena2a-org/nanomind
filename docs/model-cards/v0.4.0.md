# Model Card: nanomind-security-classifier v0.4.0

**Released:** 2026-04-09
**Status:** latest
**Corpus:** sft-v9 (augmented with sft-v8)
**Previous Version:** v0.3.0
**Trained By:** Automated training pipeline

## Summary

First 10-class model. Adds steganography as the 10th attack class to distinguish malicious Unicode manipulation (zero-width payloads, bidi attacks, homoglyph substitution) from benign Unicode (emoji, CJK, Cyrillic, Arabic, Indic scripts). Fixes false positives where HMA and ai-trust flagged packages like @upstash/context7-mcp as CRITICAL for having emoji variation selectors and i18n badges with Cyrillic text.

### Data Augmentation

sft-v9 base corpus (3,168 samples, 10 classes at ~318/class) augmented with 169 samples from sft-v8 for 7 attack classes: exfiltration (+21), injection (+29), privilege_escalation (+26), persistence (+18), credential_abuse (+37), lateral_movement (+15), social_engineering (+23).

v8 policy_violation excluded from augmentation because v8 policy_violation samples contain content that was correctly relabeled as steganography in v9. Including them confused the model (8 stego samples were misclassified as policy_violation in an earlier training attempt).

v8 benign class excluded because v9's benign class includes 298/320 samples with non-ASCII Unicode (emoji, CJK, Cyrillic, Arabic, Indic). v8 benign had only 4 such samples. Using v8 benign caused the model to learn "Unicode = steganography" (50 benign samples misclassified as stego in an earlier attempt).

## Known Limitations

1. **Exfiltration F1 at 0.840** (below 0.90 target). Only 24 eval samples for this class -- metrics are noisy (each misclassification swings F1 by ~0.04). Confusion matrix shows 2 exfiltration samples misclassified as injection, 1 as credential_abuse. Root cause: semantic overlap between "exfiltrate data" and "abuse credentials to extract data." Fix: add 100+ diverse exfiltration examples with clear exfiltration-specific signals in next corpus.

2. **Holdout merged into eval.** The sft-v9 eval set had only 194 samples (some classes as low as 11 samples). Holdout (204 samples) was merged to get 398 total. This means there is no independent holdout set for this version. Cross-corpus validation is not available.

3. **No adversarial robustness testing.** The adversarial benchmark dataset does not exist yet. The model has not been tested against evasion techniques (typo injection, synonym substitution, encoding tricks).

4. **No latency benchmark.** Inference latency has not been formally measured for this version. Based on v0.3.0 (same architecture, similar size), expected p99 < 5ms on M4 Max.

5. **Steganography class is new.** Only tested on generated examples. No real-world steganography attacks have been observed in the wild yet. The class may need refinement when real attack patterns emerge.

6. **Word-level tokenizer.** The SimpleTokenizer splits on whitespace, which means zero-width characters embedded within words are part of the token (e.g., "seq\u200Bueliz\u200Be" is one token). This works for detection (unusual tokens are suspicious) but may miss subtle single-character insertions.

7. **English-only attack examples.** All training data is in English. Attacks in other languages would use different keywords and may not be detected.

## Decision Log

| Decision | Rationale |
|----------|-----------|
| Added steganography as 10th class | False positives on emoji/i18n packages (context7-mcp incident) |
| Augmented with v8 attack data | v9 alone had 318/class, causing regression vs v0.3.0 accuracy |
| Excluded v8 policy_violation | Contaminated with stego-labeled content (caused 8 misclassifications) |
| Excluded v8 benign | v8 benign lacked Unicode diversity (caused 50 benign->stego misclassifications) |
| Increased vocab 4000 -> 6000 | Better Unicode token capture for steganography detection |
| Merged holdout into eval | Eval set too small (194 samples, some classes < 15) |
| Kept d_model=128, layers=8 | Larger models (192d/10L) did not improve accuracy on this data size |

## Reproduction

```bash
cd ~/workspace/opena2a-org/nanomind

# Step 1: Build augmented corpus
python3 -c "
import json, os
from collections import Counter
base = '../nanomind-training/corpus'
v8_train = json.load(open(os.path.join(base, 'sft-v8/train.json')))
v9_train = json.load(open(os.path.join(base, 'sft-v9/train.json')))

v8_by_class = {}
for s in v8_train:
    cls = s.get('attackClass', 'benign')
    v8_by_class.setdefault(cls, []).append(s)

combined = list(v9_train)
v9_inputs = set(s.get('input', '')[:100] for s in v9_train)

for cls in ['exfiltration', 'injection', 'privilege_escalation', 'persistence',
            'credential_abuse', 'lateral_movement', 'social_engineering']:
    v9_count = len([s for s in combined if s.get('attackClass') == cls])
    needed = 400 - v9_count
    if needed > 0 and cls in v8_by_class:
        for s in v8_by_class[cls]:
            if s.get('input', '')[:100] not in v9_inputs:
                combined.append(s)
                v9_inputs.add(s.get('input', '')[:100])
                needed -= 1
                if needed <= 0: break

out = '/tmp/sft-v9-augmented'
os.makedirs(out, exist_ok=True)
json.dump(combined, open(os.path.join(out, 'train.json'), 'w'), indent=2, ensure_ascii=False)

v9_eval = json.load(open(os.path.join(base, 'sft-v9/eval.json')))
v9_holdout = json.load(open(os.path.join(base, 'sft-v9/holdout.json')))
json.dump(v9_eval + v9_holdout, open(os.path.join(out, 'eval.json'), 'w'), indent=2, ensure_ascii=False)
"

# Step 2: Train
python3 training/scripts/train-tme-mlx.py \
  --corpus-dir /tmp/sft-v9-augmented \
  --output-dir training/models-tme-v6 \
  --epochs 300 --batch-size 64 --layers 8 --d-model 128 \
  --dropout 0.1 --lr 0.001 --patience 50 --vocab-size 6000

# Step 3: Export ONNX
python3 training/scripts/export-onnx.py --model-dir training/models-tme-v6

# Step 4: Verify hashes
for f in tokenizer.json nanomind-tme.onnx nanomind-tme.onnx.data; do
  echo "$f: $(shasum -a 256 training/models-tme-v6/$f | cut -d' ' -f1)"
done
```

Note: Due to random seed = 42 and deterministic MLX operations, results should be reproducible on the same hardware. Different hardware (Intel vs ARM, different GPU) may produce slightly different weights due to floating point ordering.
